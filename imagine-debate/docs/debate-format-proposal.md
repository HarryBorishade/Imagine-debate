# Proposal: a more interactive Imagine Debate

Status: The first version is implemented locally as **Open exchange**, alongside the existing Structured mode. A read-only check on 20 November 2026 found that the specified live Supabase project lacked the mode column and unranked constraint, and did not list the delete-account Edge Function. No database changes or deployments were made. The repository does not contain a complete baseline schema, so verify the actual database before applying the migration. The original proposal below includes future ideas that are not yet implemented.

## Implemented first version and deployment

Open exchange has eight turns: FOR then AGAINST open; AGAINST then FOR speak in each of two open exchanges; AGAINST then FOR close. Each can ask questions or respond freely within the current 100-word limit. The creator chooses an existing turn timer (30?300 seconds, default 120), and the mode is always unranked. Questions are ordinary text: message types, reply links and saved pass/timeout events remain ideas, not implemented features. Both modes use the existing AI scoring, forfeit handling and in-memory room state. An opponent can review the mode and timer in the lobby. The judge and outcome transcript display the exchange as such, while legacy message stage values remain compatible.

Before enabling this live: inspect the actual schema, policies and migration history and test with a backup in staging. Apply `supabase/migrations/20261120120000_debate_modes.sql` **before** deploying code that reads the new column; then deploy the Socket.IO backend, the `judge-debate` Edge Function, and finally the frontend. Deploy all of them: a frontend deployment alone cannot enable the mode. The migration defaults existing rows to classic and enforces unranked open exchange. Test old and new debates with two real accounts, both sides, timer expiry, reconnects, forfeits, appraisals and rating changes before production use. Roll back new creation first; retain compatible server/judge support for active open exchanges. No live migration or deployment has been performed.

Known limitations: room state and drafts still disappear on server restart; multiple servers do not share this state. Passes/timeouts are not stored as events; questions cannot be linked to specific messages; a debate without a message from both sides cannot be judged. The server now serializes each in-process turn and extends a timed-out turn when its draft cannot be saved; multi-instance concurrency, restart recovery and database persistence still require further hardening. The later implementation ideas below describe further work, not the current release.


## The problem

The live format follows seven prescribed stages: opening statement, primary claim, evidence, explanation, rebuttal, counter-rebuttal and closing statement. Both players speak once in each stage, always FOR then AGAINST: up to 14 turns. At the default 120 seconds per turn, that is up to 28 minutes of turn time, excluding transitions and judging; people can submit earlier or pass. Each message is limited to 100 words. The labels force ideas into separate boxes even when a natural response would combine a claim, evidence and a challenge. Players must wait for their turn and cannot explicitly connect a question or response to a particular message. This is a plausible engagement problem, not a measured finding: confirm it with users and completion data.

## Recommendation: Guided Conversation

The original proposal was to pilot a second, unranked format that retains turn-taking and clear boundaries but makes the middle of the debate a conversation. Keep the current format available for existing and already-created debates. Example motion: “Remote work is more productive than office work.”

1. **Opening:** FOR and AGAINST each post one position, up to 100 words and 90 seconds per turn. Example: “Remote work gives people uninterrupted focus.”
2. **Exchange:** Four alternating turns, starting with AGAINST, then FOR, AGAINST, FOR. The speaker chooses **Response** or **Question**, optionally selects an opponent's earlier message, and writes up to 100 words within 90 seconds. Example question: “How do you account for the loss of informal mentoring?” The next speaker sees the selected message and question in context; they may answer, challenge or raise another point. Questions are part of the normal turn, not a separate unlimited chat.
3. **Closing:** AGAINST closes, then FOR closes, once each, within the same limits. Both see the complete conversation and receive feedback.

This gives each side four turns, with alternating first speaker across phases. There are eight turns maximum, or 12 minutes of turn time at 90 seconds, plus transitions and judging. The existing time choices should not be assumed to apply: for the pilot fix 90 seconds and explain it in the lobby. A question does not guarantee an answer and carries no automatic penalty; the judge can assess the substance of a response. Offer optional on-screen prompts such as “What is your strongest reason?” and “What would change your mind?” without forcing a type of argument. A simple reply link and visible question badge make the exchange easier to follow; no simultaneous messages, spectator voting, AI interruptions, or extra paid services are needed for the first test.

Pass and timeout consume the current turn; timeout submits a valid saved draft if present, otherwise records a pass. Clearly show the next speaker, time left and remaining turns. Record passes and timeouts as events so both players and the judge can distinguish silence from missing data. Give participants the existing disconnect grace period, pause the clock during it, and explain the consequence of leaving. Do not score a normal completion without at least one valid message from each side; show an explicit incomplete outcome rather than leave judging failed. Define the treatment of a voluntary early end later; for the pilot use the existing leave/forfeit flow.

## Why test it

The opportunity is to reduce waiting and let players respond to a specific claim without abandoning fairness or a manageable transcript. Test whether that actually improves engagement with a small opt-in cohort, comparing like-for-like unranked debates with the existing format. Ask both players whether they felt heard, had enough time, and would debate again. Track starts, normal completions, duration, passes/timeouts, reconnections, judging failures and voluntary repeat debates by format version; define event consent and avoid logging argument text in analytics. Compare samples and abandonment reasons rather than assuming shorter is better. Review a few volunteered transcripts for unanswered questions and fairness. Initial decision rule: keep iterating if completion and repeat participation improve without a material rise in complaints or failures; agree sample size and thresholds before launch. Existing GA events require consent and cannot be treated as complete population data.

## What exists today

- The Next.js frontend creates a four-digit debate code, topic, optional description, ranked choice and turn duration in `debates`; users join a two-person lobby, choose opposing sides and ready up. Default is ranked and 120 seconds; available durations are 30, 60, 120, 180 and 300 seconds. See `frontend/app/debate/create/page.tsx` and the lobby page.
- `backend/src/socketServer.ts` authenticates sockets with Supabase, orchestrates the seven stages and timers, enforces turn and word limits and persists messages. Active rooms, drafts, turns and timers are process memory. A reconnect can restore an existing room while that process remains alive, but a restart loses it. The optional Redis Socket.IO adapter distributes events; it does not make this in-memory room state durable or automatically make multiple workers safe.
- A timeout can auto-submit the latest synced draft, or skip an empty turn; explicit passes also advance. A disconnect pauses the timer for a 15-second grace period; leaving or failing to reconnect can forfeit. Normal completion queues AI appraisal; forfeits use a different result path.
- `messages` stores the sender, side, content, `argument_part`, `stage_index` and `turn_index`. History and outcome pages use these fields; `debates.id` is text while `messages.debate_id` is a bigint in the checked-in function. The outcome page contains its own mapping of stage labels.
- `supabase/functions/judge-debate/index.ts` reads the ordered transcript and asks Gemini to score logic, evidence, rebuttal, clarity and conduct, each out of 20. It requires at least one message per side, stores appraisal on `debates` and applies ranked results through `apply_debate_result`. It may request a stronger review. Ranked/unranked and reporting were added in the later checked-in migration. These observations describe code, not verified production configuration.
- `General Architecture.txt` and `Tech Stack.txt` are older planning notes, not authoritative descriptions: for example, the running debate engine is Socket.IO, not solely Supabase Realtime, and the current judge stores results on `debates` rather than the proposed `judge_results` table.

## Implementation and Supabase work

1. **Inspect first.** Back up production; compare deployed migration history, actual tables, constraints, grants, RLS policies, indexes, RPCs and Edge Function versions with this repository, including older permissive policies. The checked-in migrations modify pre-existing tables and are not a complete setup script. Test in a separate Supabase project or local copy using non-production data. Do not paste speculative SQL into production.
2. **Version the format.** Add a non-null `debates.format_version` through a reviewed migration, defaulting/backfilling existing rows to e.g. `classic_v1`; use `guided_v1` only for new opt-in rooms. Restrict accepted versions and ensure browser insert permissions and RLS cannot create invalid combinations. Persist the chosen duration and ranked setting at creation; enforce `guided_v1` as unranked on the server/database for the pilot, not just in the UI. Existing active rooms must finish on their original version; old transcripts and results must continue to render.
3. **Extend the transcript safely.** Add nullable message metadata for `message_type` (`statement`, `response`, `question`) and `reply_to_message_id`, with suitable constraints, indexes and validation. Inspect existing ID types first. A reply target must belong to the same debate and be an earlier opponent message; validate in the trusted server or a transactional RPC, not just the browser. Map null legacy fields to classic display. Model passes/timeouts in a separate participant-readable, server-write-only `debate_events` table, ordered with messages by an authoritative sequence (or a unified event log). Avoid relying solely on timestamps; assign sequence numbers atomically. Retain existing `argument_part`, `stage_index` and `turn_index` until all old readers have a compatibility path. Check any existing enum/check constraints before choosing new values.
4. **Make transitions authoritative and recoverable.** Implement a versioned phase/turn state machine, validating membership, side, expected turn, type, word limit, deadline and reply target for every action. Commit the event/message and turn advancement atomically with an idempotency key and expected state/version so retries, duplicate submissions and timeout races cannot produce two turns or skip one. Persist phase, next speaker, sequence, deadline and paused/disconnected state; on reconnect or restart rebuild the room from durable state. Decide and test a single authority for deadlines and recovery, including a worker or startup sweep for expired turns. Redis event broadcasting alone is insufficient. Ensure a failed timeout save does not silently advance, and apply the same content checks to manual and auto-submitted drafts. Preserve existing forfeit and idempotent result handling.
5. **Update UI and judging.** Add a clearly labelled format selector, default classic during the pilot, and explain duration, unranked status and rules before both players ready. Update lobby, room, transcript history, outcome, reconnect payloads and relevant help copy for both versions. Show reply context, phase, remaining turns, passes and question badges accessibly on mobile. Update the judge transcript/prompt for phase, question, reply links and skipped turns; preserve old transcripts and the existing result schema. Evaluate equal treatment, unanswered questions and incomplete debates; avoid judging a missing side. Consider whether rank eligibility should ever expand only after testing.
6. **Release in order.** Apply backwards-compatible migration in staging first; deploy backend and judge capable of reading both formats, then frontend behind a disabled-by-default feature flag. Verify two real accounts, both sides and old/new transcripts, ranked results and forfeits. Enable only the unranked pilot, monitor, and keep classic as a rollback path. Disable new guided creation if issues occur, but retain compatible backend/judge support until any active guided debates finish; never delete data to roll back. Deploy the reviewed migration, backend, Edge Function and frontend separately when ready: a git push alone does not apply all surfaces. No production changes have been made by this document.

## Checks before release

- Run frontend lint/build and backend TypeScript build; add meaningful state-machine and transaction tests for both versions, duplicate sends, late sends, pass/timeout races, failed persistence and restarts.
- Exercise two real clients: normal completion, each side's turn order, question/reply links, limits, invalid/cross-debate references, reconnect, grace expiry, intentional leave and app/server restart. Verify old completed transcripts and in-flight classic debates.
- Check RLS and direct API attempts with two participants and a third account: no forged messages, changed turns, cross-debate reads or unauthorised result/rating writes. Verify actual deployed policies because permissive policies can combine.
- Test both judge success and failure/retry, empty-side completion, forfeits, and idempotent ratings. Confirm the pilot never changes ratings and does not silently create a fabricated result.

## Decisions for the product owner

- Does this 8-turn, 90-second unranked pilot feel right, or should exchanges be longer/shorter?
- Should answers to direct questions be encouraged only, or required? The recommendation is encouraged, with no automatic penalty.
- Who can see saved transcripts and how long should they be retained? Current repository policies intend participant-only access; verify actual policy before making product claims.
- Who owns staging/production Supabase access, backend hosting, Edge Function secrets and deployment? Actual providers and configuration were not verified from this workspace.
