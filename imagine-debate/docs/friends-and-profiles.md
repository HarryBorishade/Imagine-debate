# Friends, invitations and private profiles

Status: pending local release candidate. The supplied handover reports that owner-only profile reads are already applied, while friends, blocks and invitations remain pending; this session has not independently rechecked production. See [release readiness](release-readiness.md). The application is not yet ready to offer social features to minors. The local test uses synthetic users; it does not prove the live database or deployed policies match.

## User experience

Existing Auth accounts and room display names remain as they were. Under Settings, a signed-in player chooses a separate, unique public handle (3-20 ASCII letters, digits or underscores; case-insensitive uniqueness). Discovery is off by default. An exact-handle search can return only an opted-in player and their handle and user ID, never email, private profile fields or debate content. A sender needs a handle, and a recipient must explicitly accept the friend request. Pending requests can be declined or cancelled; friendships can be removed. A player can block and later unblock someone they find or already know. Blocking removes the friendship and pending invitations and stops a blocked pair from starting a new debate through the database start trigger. It does not end an already-running debate, and the app does not yet offer a block button for an unknown opponent in a room.

From Friends, select Invite to debate, create a debate, and the app creates an in-app invitation to the accepted friend. The recipient opens Friends and joins the waiting room; opening the invite is retryable until the room starts or the invite is dismissed. If notification/invite creation fails after a debate is created, the creator receives a link to the existing lobby rather than accidentally creating duplicate rooms. This is not an exclusive invitation: the existing four-digit room code still permits anyone who knows or guesses it to attempt to join. Existing rooms and live events retain their current behaviour. There is no email, push notification or automatic refresh; players can refresh the Friends page.

## Database and privacy

`supabase/migrations/20261121152000_private_friends_and_invites.sql` adds separate social profile, relationship, block, invite and per-account rate-limit tables. Clients have no direct table access; RPCs validate identity, acceptance, ownership and blocked relationships, and return only the fields needed. Pair-changing operations use transaction advisory locks. A trigger checks blocks when a debate becomes active. Search is exact and limited to 30 requests per account per hour; public-handle updates, requests and invitations have separate limits. These are not IP-level limits and do not prevent automated attacks from many accounts. Because handles must be unique, an unavailable-handle response can reveal that a hidden handle is already taken; the profile-update limit reduces but does not eliminate that side channel.

The block list returns a neutral `Blocked player` label for accounts that opted out of discovery, while retaining the ability to unblock them.

The migration removes existing RLS policies on `profiles` and replaces them with owner-only reads, revokes browser writes, and introduces service-controlled RPCs. This is intentional: the old migration's broad SELECT policy exposed all legacy profile columns to signed-in users, even when the new handle setting is private. The dashboard only reads the current user's profile in this checkout, while the report function uses service role; other deployed consumers, legacy policies, column privileges, functions, triggers and schema drift must be audited before application. The existing Auth username update and profile-sync triggers remain separate from the public social handle. Enforcing a profanity policy for handles, topics and usernames needs further work; the existing message filter does not cover those paths.

## Before deployment

1. Coordinate with the other Supabase session: inspect live schema, grants, all policies and migration history, and obtain a backup that passes a complete restore test. The previous backup had an unresolved function-execution permission mismatch. Test against an isolated staging copy first. The supplied handover reports the newer debate-mode migration as applied; reconcile actual history and schema before deciding what is pending.
2. Run `backend/tests/social-fixture.sql`, the migration, and `backend/tests/social-rls.sql` only on a fresh disposable local Supabase instance using test users. The SQL tests cover owner-only profile reads, direct-access denial, exact opt-in search, case-insensitive uniqueness, rate limiting, sender/recipient authorization, friend acceptance, invitations, blocking and the debate-start guard. Also perform two-account UI tests in staging; no production account or real friend invitation was used here.
3. Implement durable production rate limiting and abuse monitoring, a block/report action available from a debate or opponent profile, appropriate support staffing and a verified monitored mailbox. Add a recovery/removal workflow for inappropriate handles. The current code cannot reliably stop an active debate immediately on a newly created block.
4. Complete the child-safety and privacy assessments and implement age-appropriate safeguards for the intended 13-17 audience before launch. Existing four-digit room codes are enumerable, the connection model has no verified age or school membership, and blocking and word filtering do not by themselves make interaction safe. Under-13 and school-managed access require a separate design. See `docs/release-privacy-safety.md`.
5. Review data retention and erasure for connections, invitations, rate-limit rows and blocked lists, privacy disclosures, legal bases and notifications with the operator/adviser. Foreign keys cascade on account deletion, but the live deletion function and provider/backups must be verified separately.
